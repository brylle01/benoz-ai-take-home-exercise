  The format

  One optional top-level key, rules, sibling of fields. The worked example is
  live in clients/client-b-grant-foundation.json:

  {
    "id": "end_date_not_before_start_date",
    "assert": { "field": "project_end_date", "op": "gte", "other_field":
  "project_start_date" },
    "error": { "field": "project_end_date",
               "message": "Project end date must not be before the project start
  date" }
  }

  A rule reads as a sentence: when (optional guard), assert this, otherwise
  report this message against this field. when and assert share one condition
  grammar — field + op + either a literal value or an other_field (that's how a
  rule names its dependency), plus all_of/any_of to combine. Twelve operators,
  covering ordering, membership, multi-choice containment and presence.

  Rules sit at the top level rather than on a field, because hanging one off
  project_end_date hides it from whoever is reading project_start_date — the
  field they're about to change.

  The three judgment calls

  Error target: the subject of the assert, overridable via error.field. One rule
  → at most one error, never two; highlighting both ends of a comparison claims
  two problems where there's one.

  Missing/invalid dependency: the rule runs only if every field it reads is
  usable — present, and free of phase-1 errors. Otherwise skipped silently,
  because "15/01/2027" >= "2027-12-15" isn't false, it's meaningless, and
  reporting it sends the user to fix the wrong field. present/absent are the
  carve-out that makes "required if" expressible. The silence is bounded:
  malformed rules, unknown operators, and incomparable operands are all reported
  loudly — a rule that always passes is worse than no rule.

  Where I stopped: a rule can read and compare values, never compute one. No
  arithmetic, no "within 90 days", no cross-record lookups, no
  rule-depends-on-rule. The test is that every rule reads aloud as one English
  sentence.

  Two additions beyond the ask

  - validateDefinition(definition) — rules ship as JSON and JSON has no
    compiler, so a mistyped field name would otherwise become a rule that
    silently never fires. It catches unknown fields/operators, duplicate ids,
    missing messages, malformed operands, and date-against-number comparisons.
  - Order-independence as a guarantee, with a test asserting it. Rules read
    phase 1 and the record, never each other, so reordering the array can't
    change the result and the user sees all problems at once.
